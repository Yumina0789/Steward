# 0003 人用账户，机器用服务 token

## 状态

已接受（2026-10-09）

## 背景

面板最初只有一串 token：打开链接、粘进输入框、记在浏览器里。对机器调用这很合适（一行
`curl -H "Authorization: Bearer …"` 就完事），对人就很难受 —— 一串 32 位随机字符既记不住
也说不清「谁登录了」，而且没法改、没法撤、没法给第二个人开一个。

但把 token 直接删掉也不行：Steward 每 60 秒要用它去 Nimbus 拉限流决策（
`/api/enforce/pending`），那种调用没有「人」可以登录 —— 半夜三点也要能跑。

## 决策

**两套凭证并存，用途分开：**

* **账户 + 密码**（人用）：第一次打开面板时先设置一个账户，之后用用户名 + 密码登录。
  密码用 scrypt 加盐存（标准库自带）；登录成功发一个 **7 天有效的会话令牌**，可撤销、
  可「退出所有会话」；同一来源 5 分钟内失败 8 次就临时拒绝，给暴力破解上摩擦。
* **服务 token**（机器用）：`steward.token` / `nimbus.token` 照旧有效，仍然能调整个 API。
  它只存在服务器上（0600），不出现在浏览器里。

账户存在数据目录下的 `accounts.json`（0600）：Nimbus 是 `/var/lib/nimbus/`，Steward 是
`/var/lib/steward/`。忘了密码可以直接删掉这个文件重启（回到「首次设置」状态）——
这是刻意留的运维后门，也是不用数据库的原因之一。

## 后果

* 好的一面：人能像正常网站一样登录、改密码、开第二个账户（家里两个人各一个）；机器
  调用不受影响，Steward↔Nimbus 的自动化一条都不用改；token 泄漏的影响面从「面板」变成
  「面板 + 机器接口」—— 所以它仍然只放在服务器上。
* 差的一面：**多了一个长期密钥要管**。服务 token 不随账户失效，改密码不会让它失效；
  要换就改文件再重启服务。
* 凭证校验的代码在两个项目里各有一份（它们刻意不共享代码），所以每处改动都要同步做两遍。

## 备选方案

1. **只留账户、删掉 token**：Steward 的自动执法会断，或者要给它建一个「机器账户」并
   把密码写在配置里 —— 那其实就是 token，只是更难轮换。
2. **只留 token、用 HTTP Basic 包一层**：省事，但 Basic 没有会话、没有撤销、每次请求
   都带密码，也仍然说不清「谁登录了」。
3. **接 OAuth / 外部身份**：为一个管自己一台机器的面板引第三方依赖，代价远大于收益。
